# 0부 · 준비 (한 번만)

## 0-1. 공용 레포 만들기 — 한 사람이

**세 명이 같은 코드를 만져야** "동료의 변경이 나에게 도착하는" 상황이 만들어집니다.
빈 폴더에서 시작하면 1부의 작업 지시가 가리킬 코드가 없으므로, 먼저 뼈대를 넣습니다.

```sh
gh repo create hankki-demo --public --clone --add-readme && cd hankki-demo
```

> `gh` 가 없으면 https://github.com/new 에서 `hankki-demo` 를 Public + README 로
> 만들고 클론하세요.

아래를 **통째로** 붙여넣습니다. 서로 물려 있는 파일 넷이 들어갑니다 —
한 사람이 타입을 바꾸면 다른 사람이 영향을 받는 구조여야 이 도구가 하는 일이 드러납니다.

```sh
mkdir -p lib cart order delivery

cat > lib/types.ts <<'EOF'
export type MenuItem = { id: string; name: string; price: number };
export type CartLine = { item: MenuItem; qty: number };
export type OrderStatus = "pending" | "cooking" | "delivering" | "done" | "canceled";
export type Order = { id: string; lines: CartLine[]; status: OrderStatus; placedAt: string };
EOF

cat > cart/total.ts <<'EOF'
import type { CartLine } from "../lib/types";

/** 장바구니 합계. 아직 배달비·할인이 빠져 있다. */
export function cartTotal(lines: CartLine[]): number {
  return lines.reduce((n, l) => n + l.item.price * l.qty, 0);
}
EOF

cat > order/cancel.ts <<'EOF'
import type { Order } from "../lib/types";

/** 취소 가능 여부. 조리가 시작되면 못 되돌린다는 규칙만 있다. */
export function canCancel(order: Order): boolean {
  return order.status === "pending";
}
EOF

cat > delivery/eta.ts <<'EOF'
import type { Order } from "../lib/types";

/** 배달 예상시간(분). 지금은 고정값이라 실제와 어긋난다. */
export function estimateMinutes(_order: Order): number {
  return 30;
}
EOF

git add -A && git commit -m "init: 장바구니 · 주문취소 · 배달ETA 뼈대" && git push
```

나머지 두 사람은 클론합니다:

```sh
git clone https://github.com/<계정>/hankki-demo.git && cd hankki-demo
```

> **세 명 모두 같은 폴더 이름·같은 레포**여야 합니다. 각자 다른 레포를 쓰면
> 요약은 올라가지만 "같은 코드를 함께 만진다" 는 장면이 안 만들어집니다.

## 0-3. Jira 이슈 만들기 — 한 사람이

`KAN` 프로젝트에 다섯 개를 만듭니다. **전부 담당자(Assignee)를 지정하세요** —
담당자가 없으면 그 이슈는 어느 회의에도 근거로 붙지 않습니다.

| 키 | 제목 | 서브태스크 | 담당자 | 우선순위 |
|---|---|---|---|---|
| KAN-1 | 장바구니 담기 기능 | 3개 — **전부 Done** | 이중희 | Medium |
| KAN-2 | 주문 취소 플로우 | 3개 — **2개만 Done** | 창현 | Medium |
| KAN-3 | 3.2 릴리즈 QA 체크리스트 | 4개 — **전부 Done** | 김민성 | Medium |
| KAN-4 | 결제 실패 시 이중 청구 | 없음 · **미완** | 창현 | **Highest** |
| KAN-5 | 배달 예상시간 오차 | 없음 · 미완 | 김민성 | Medium |

서브태스크는 이슈를 연 뒤 `Add a child` 로 만듭니다. 이름은 아무거나 (`API` ·
`화면` · `테스트` 정도). **완료 표시는 상태를 `Done` 으로 옮기면 됩니다.**

> 왜 이 모양인가: `KAN-1` 은 "다 끝난 일", `KAN-2` 는 "아직 남은 일",
> `KAN-3` 은 릴리즈 선행 조건, `KAN-4` 는 결정을 만들어 낼 P1 결함입니다.
> 각각이 뒤에서 다른 판정을 만듭니다.

# 1부 · 훅을 돌린다 (15분)

회의 판정의 핵심 조건 하나가 **"참석 후보 전원이 이 내용을 이미 주입받았는가"** 입니다.
그걸 만들려면 세 명이 **각자 두 번씩** 세션을 돌려야 합니다.

- 1바퀴: 각자 작업 → 세션이 끝나면 요약이 서버로 올라감
- 2바퀴: 각자 새 세션 시작 → **그때 남들 요약이 내 에이전트에 주입됨**

> 세션 요약이 **300자 미만이면 건너뜁니다.** 아래 프롬프트는 그보다 길게 나오도록
> 만들었지만, 짧게 끝났다면 `TEAMSYNC_FORCE=1 claude` 로 띄우세요.

## 1바퀴 — 세 명이 동시에

각자 자기 폴더에서 `claude` 를 띄우고 아래를 그대로 붙여넣습니다.
**작업이 끝나면 세션을 종료**(`/exit` 또는 Ctrl-D)해야 요약이 올라갑니다.

### 이중희 — 장바구니 (`KAN-1`)

```
cart/total.ts 를 실제로 쓸 수 있는 수준으로 올리자. lib/types.ts 를 먼저 읽고 시작해줘.

1. 같은 메뉴를 두 번 담으면 줄이 늘지 않고 수량만 올라가도록 addLine 함수 추가
2. 수량을 0으로 내리면 그 줄을 빼는 removeLine 추가
3. 배달비를 합계에 더하되, 2만원 이상이면 무료가 되도록 cartTotal 확장
4. 각 함수에 무엇을 왜 그렇게 했는지 주석으로 남겨줘

lib/types.ts 에 새 타입이 필요하면 거기에 추가해도 돼. 다른 사람이 쓰는 파일이니
바꾼 부분은 마지막에 따로 정리해서 알려줘.
```

### 창현 — 주문 취소 (`KAN-2`)

```
order/cancel.ts 를 확장하자. lib/types.ts 와 order/cancel.ts 를 먼저 읽어줘.

1. 취소 사유를 받는 CancelReason 타입을 만들고, cancelOrder 함수를 추가
2. 조리 시작 이후에는 취소 대신 "취소 요청" 상태로만 넘어가도록 규칙 추가
3. 이미 배달중이거나 완료된 주문은 어떤 경우에도 취소 불가로 막아줘
4. 각 규칙이 왜 그런지 주석으로 남겨줘

결제 환불 연동은 하지 마. 부분 환불로 할지 전액으로 할지가 아직 안 정해졌어.
그 부분은 TODO 주석으로만 남겨줘.
```

### 김민성 — 배달 예상시간 (`KAN-5`) + 릴리즈 점검 (`KAN-3`)

```
delivery/eta.ts 가 30분 고정이라 실제와 어긋나. 고쳐보자.
lib/types.ts 와 delivery/eta.ts 를 먼저 읽어줘.

1. 주문 줄 수와 메뉴 개수에 따라 조리시간이 늘도록 계산 추가
2. 주문 시각(placedAt)이 점심·저녁 피크면 배달시간을 더하도록 처리
3. 계산 결과가 항상 최소 15분 이상이 되도록 하한 적용

그리고 지금 코드 전체를 훑어서, 3.2 릴리즈 전에 손봐야 할 게 뭐가 남았는지
우선순위와 함께 목록으로 정리해줘. 고치지는 말고 목록만.
```

작업이 끝나면 각자 푸시합니다. 세 사람이 `lib/types.ts` 를 같이 건드렸을 테니
충돌이 나면 그것 자체가 좋은 장면입니다 — **바로 그래서 서로의 작업을 알아야 합니다.**

```sh
git add -A && git commit -m "작업" && git pull --rebase && git push
```

> 요약은 푸시와 무관하게 세션 종료 시점에 이미 올라갑니다. 푸시는 코드를 맞추기
> 위한 것이지 판정을 위한 것이 아닙니다.

**세 명 모두 세션을 종료했는지 확인하고 다음으로 넘어갑니다.**

## 장면 1 — 회의가 사라진다 `DELETE`

> 가장 강한 장면입니다. 먼저 하세요.

**신청자: 이중희**

```
장바구니 담기 기능 어디까지 됐는지
주문 취소 플로우 진행 상황

**나와야 할 결과: `DELETE` — 회의가 열리지 않습니다.**

화면에서 짚을 것:

- **조건 6개가 전부 PASS.** 특히 `이미 전달됨` — *"참석 후보 3명 전원이 이 내용을

- **`해석 모호성 없음`** — Jira 가 Task 단위로 세어 줬기 때문입니다.
- 근거 목록의 **`부른 사람`** 배지 — 신청자가 이슈 번호를 하나도 안 적었는데
  근거가 붙었습니다. 부른 사람들이 최근에 건드린 것을 찾아온 겁니다.

> 안 되면: `데이터 최신` 이 FAIL 이면 세션이 3시간보다 오래된 것입니다.
> 아무나 짧게 세션 하나 더 돌리고 다시 내세요.

## 장면 2 — 결정 하나만 남는다 `DECIDE`

**신청자: 김민성**

| 칸 | 넣을 것 |
|---|---|
| 제목 | `3.2 릴리즈 Go / No-Go` |
| 이 회의가 끝나면 | `출시 여부 결론` |
| 참석 | 전부 체크 |
| 시간 | `60` |

안건:

```
QA 체크리스트 다 끝났는지 확인
결제 이중 청구 결함(KAN-4)을 안고 출시할 것인가
```

**나와야 할 결과: `DECIDE` — 회의 대신 결정 카드 한 장.**

화면에서 짚을 것:

- **`결정 카드 보기`** 로 들어가면 **"왜 제가 받았나요"** 가 적혀 있습니다.
  수신자는 상수가 아니라 규칙으로 뽑고, 그 규칙 문장을 같이 싣습니다.
- 선택지가 **`그대로 진행` / `보완 후 진행`** 두 갈래인데,
  `cons` 에 **P1 결함 1건** 이 박혀 있습니다 — Jira 의 `KAN-4` 에서 온 숫자입니다.
- 마감이 **회의 예정 시각**입니다. 그 전에 답이 나오면 회의가 필요 없습니다.

**여기서 `보완 후 진행` 을 선택하세요.** 뒤에서 씁니다.

> `Prerequisite 충족` 이 FAIL 이면 `KAN-2` 의 남은 서브태스크가 걸린 겁니다.
> 그게 정상 동작입니다 — 그대로 보여주셔도 좋습니다("아직 남은 게 있으니 NO-GO").
> `DECIDE` 를 보시려면 `KAN-2` 를 전부 Done 으로 옮기고 다시 내세요.

| 제목 | `주문 취소 시 환불 처리 방식` |

안건:

```
주문 취소 플로우 지금 어디까지 됐는지
부분 환불을 지원할지 전액 환불만 할지
PG사 환불 API 응답이 늦을 때 어떻게 보여줄지
```

**나와야 할 결과: `SHRINK` 또는 `DECIDE` — 회의가 줄어듭니다.**

화면에서 짚을 것:

- **빠진 안건**: "어디까지 됐는지" 는 확인하면 끝나는 것이라 회의에서 빼냅니다.
- **참석자가 줄어듭니다.** 각자 왜 남았는지 / 왜 빠졌는지 이유가 붙습니다 —
  *"이미 내용을 주입받았습니다. 앉아 있을 이유가 없습니다."*
- **종료 조건**이 시간이 아니라 조건으로 적혀 있습니다.

## 장면 7 — 원인을 AI가 고르지 않는다 `SHRINK`

**신청자: 창현**

결제가 두 번 청구되는 원인이 무엇인지
```

- 지금 가장 유력하다고 보는 원인: `PG 응답 지연으로 재시도가 두 번 나감`
- 아직 배제하지 못한 다른 가능성:

```
클라이언트 중복 클릭
웹훅 재전송 처리 누락
```

화면에서 짚을 것:

  **여기서 AI 는 하나를 고르지 않습니다** — 판단을 사람에게 넘깁니다."*

  결론이 바뀝니다. 두 번 내서 비교해 보여주면 좋습니다.
