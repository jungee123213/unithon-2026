# 0부 · 준비 (한 번만)

## 0-1. 공용 레포 만들기 — 한 사람이

**에이전트를 쓰는 셋이 같은 폴더를 공유해야** 합니다. 개발자 둘은 코드를 만지고,
디자이너는 그 옆에 스펙 문서를 씁니다. 빈 폴더에서 시작하면 가리킬 대상이 없으므로
먼저 뼈대를 넣습니다.

```sh
gh repo create hankki-demo --public --clone --add-readme && cd hankki-demo
```

> `gh` 가 없으면 https://github.com/new 에서 `hankki-demo` 를 Public + README 로
> 만들고 클론하세요.

아래를 **통째로** 붙여넣습니다. 파일 넷이 들어갑니다.

**세 사람이 각자 다른 파일만 만집니다.** `lib/types.ts` 는 공용이라 아무도 고치지
않습니다 — 그래야 병합 충돌로 시간을 버리지 않습니다. "동료의 변경이 나에게
도착한다" 는 git 이 아니라 **훅이 요약을 주입해서** 일어나는 일입니다.

| 파일 | 담당 |
|---|---|
| `lib/types.ts` | **공용 · 아무도 수정하지 않음** |
| `cart/total.ts` | 이중희 (개발) |
| `order/cancel.ts` | 창현 (개발) |
| `design/` | 김민성 (디자인) — **마크다운 스펙만. 코드 아님** |

> **클론하는 사람은 셋(이중희 · 창현 · 김민성)입니다.** PM · 마케터는 웹만 씁니다.
>
> 디자이너가 클론하는 이유는 코드 때문이 아니라 **훅이 git 저장소 안에서만
> 동작하기 때문**입니다. 저장소 밖에서 `claude` 를 띄우면 브랜치를 못 읽어
> 요약이 조용히 안 올라갑니다.

```sh
mkdir -p lib cart order design

cat > lib/types.ts <<'EOF'
// 공용 타입. 둘이 함께 쓰므로 이 파일은 수정하지 않는다.
// 새 타입이 필요하면 각자 자기 파일 안에 정의한다.
export type MenuItem = { id: string; name: string; price: number };
export type CartLine = { item: MenuItem; qty: number };
export type OrderStatus = "pending" | "cooking" | "delivering" | "done" | "canceled";
export type Order = { id: string; lines: CartLine[]; status: OrderStatus; placedAt: string };
EOF

cat > cart/total.ts <<'EOF'
import type { CartLine } from "../lib/types";

/** 장바구니 합계. 아직 배달비·할인이 빠져 있다. */
export function cartTotal(lines: CartLine[]): number {
  return lines.reduce((n, l) => n + l.item.price * l.qty, 0);
}
EOF

cat > order/cancel.ts <<'EOF'
import type { Order } from "../lib/types";

/** 취소 가능 여부. 조리가 시작되면 못 되돌린다는 규칙만 있다. */
export function canCancel(order: Order): boolean {
  return order.status === "pending";
}
EOF

cat > design/README.md <<'EOF'
# 디자인 스펙

시안에서 정해진 것을 개발자가 읽을 수 있게 적어 두는 곳.
피그마 링크와 함께, 화면마다 문구 · 구조 · 동작을 남긴다.
EOF

git add -A && git commit -m "init: 장바구니 · 주문취소 · 디자인 스펙 자리" && git push
```

나머지 둘(창현 · 김민성)도 클론합니다:

```sh
git clone https://github.com/<계정>/hankki-demo.git && cd hankki-demo
```

> **셋 모두 같은 폴더 이름·같은 레포**여야 합니다. 각자 다른 레포를 쓰면
> 요약은 올라가지만 "같은 코드를 함께 만진다" 는 장면이 안 만들어집니다.

## 0-3. Jira 이슈 만들기 — **PM(허주영)이**

> 실제로도 이슈를 올리는 건 PM 입니다. 개발자가 아니라 PM 이 여기를 채우는 것이
> 이 제품의 전제입니다 — 판정은 **남이 이미 적어 둔 사실**에서만 나옵니다.

`KAN` 프로젝트에 다섯 개를 만듭니다. **전부 담당자(Assignee)를 지정하세요** —
담당자가 없으면 그 이슈는 어느 회의에도 근거로 붙지 않습니다.

| 키 | 제목 | 서브태스크 | 담당자 | 우선순위 |
|---|---|---|---|---|
| KAN-1 | 장바구니 담기 기능 | 3개 — **전부 Done** | 이중희 | Medium |
| KAN-2 | 주문 취소 플로우 | 3개 — **2개만 Done** | 창현 | Medium |
| KAN-3 | 3.2 릴리즈 QA 체크리스트 | 4개 — **전부 Done** | 이중희 | Medium |
| KAN-4 | 결제 실패 시 이중 청구 | 없음 · **미완** | 창현 | **Highest** |
| KAN-5 | 빈 화면(Empty State) 시안·스펙 | 없음 · 미완 | 김민성 | Medium |

서브태스크는 이슈를 연 뒤 `Add a child` 로 만듭니다. 이름은 아무거나 (`API` ·
`화면` · `테스트` 정도). **완료 표시는 상태를 `Done` 으로 옮기면 됩니다.**

> 왜 이 모양인가: `KAN-1` 은 "다 끝난 일", `KAN-2` 는 "아직 남은 일",
> `KAN-3` 은 릴리즈 선행 조건, `KAN-4` 는 결정을 만들어 낼 P1 결함입니다.
> 각각이 뒤에서 다른 판정을 만듭니다.
>
> **담당자는 에이전트를 쓰는 셋에게만 배정합니다.** PM·마케터에게 배정하면 그
> 이슈는 "부른 사람" 축으로 회의에 붙지만 세션 요약이 없어 조건이 어긋납니다.

# 1부 · 에이전트를 돌린다 (15분) — 이중희 · 창현 · 김민성

회의 판정의 핵심 조건 하나가 **"참석 후보 전원이 이 내용을 이미 주입받았는가"** 입니다.
그걸 만들려면 에이전트를 쓰는 세 명이 **각자 두 번씩** 세션을 돌려야 합니다.

- 1바퀴: 각자 작업 → 세션이 끝나면 요약이 서버로 올라감
- 2바퀴: 각자 새 세션 시작 → **그때 남들 요약이 내 에이전트에 주입됨**

> 세션 요약이 **300자 미만이면 건너뜁니다.** 아래 프롬프트는 그보다 길게 나오도록
> 만들었지만, 짧게 끝났다면 `TEAMSYNC_FORCE=1 claude` 로 띄우세요.

## 1바퀴 — 셋이 동시에

> PM 과 마케터는 이 부에서 할 일이 없습니다. 옆에서 지켜보다가 2부에서 회의를
> 냅니다. **지켜보는 것 자체가 장면입니다** — 이 둘은 남들이 뭘 했는지 알 방법이
> 없어서 회의를 잡게 됩니다.

각자 자기 폴더에서 `claude` 를 띄우고 아래를 그대로 붙여넣습니다.
**작업이 끝나면 세션을 종료**(`/exit` 또는 Ctrl-D)해야 요약이 올라갑니다.

### 이중희 — 장바구니 (`KAN-1`)

```
cart/total.ts 를 실제로 쓸 수 있는 수준으로 올리자. lib/types.ts 를 먼저 읽고 시작해줘.

1. 같은 메뉴를 두 번 담으면 줄이 늘지 않고 수량만 올라가도록 addLine 함수 추가
2. 수량을 0으로 내리면 그 줄을 빼는 removeLine 추가
3. 배달비를 합계에 더하되, 2만원 이상이면 무료가 되도록 cartTotal 확장
4. 각 함수에 무엇을 왜 그렇게 했는지 주석으로 남겨줘

lib/types.ts 는 다른 사람도 쓰는 공용 파일이니 **수정하지 마.** 새 타입이 필요하면
cart/total.ts 안에 정의해줘.
```

### 창현 — 주문 취소 (`KAN-2`)

```
order/cancel.ts 를 확장하자. lib/types.ts 와 order/cancel.ts 를 먼저 읽어줘.

1. 취소 사유를 받는 CancelReason 타입을 만들어줘
2. cancelOrder(order, reason) 를 추가하고, 결과를 다음 셋 중 하나로 돌려줘:
   - 바로 취소됨
   - 취소 요청만 접수됨 (조리가 이미 시작된 경우)
   - 취소 불가 (배달중이거나 완료된 경우)
3. 각 규칙이 왜 그런지 주석으로 남겨줘

lib/types.ts 는 공용 파일이니 **수정하지 마.** OrderStatus 를 늘리지 말고,
취소 결과 타입은 order/cancel.ts 안에 새로 정의해줘.

결제 환불 연동은 하지 마. 부분 환불로 할지 전액으로 할지가 아직 안 정해졌어.
그 부분은 TODO 주석으로만 남겨줘.
```

### 김민성 — 빈 화면 시안 스펙 (`KAN-5`)

**디자이너는 코드를 만지지 않습니다.** 시안에서 정한 것을 개발자가 읽을 수 있게
적어 두는 게 일입니다. 그 문서를 에이전트와 같이 씁니다.

```
design/ 폴더에 빈 화면(Empty State) 스펙을 쓰자. design/README.md 를 먼저 읽어줘.

design/empty-state.md 를 만들고 화면 세 개를 정리해줘:
  - 장바구니가 비었을 때
  - 주문 내역이 없을 때
  - 검색 결과가 없을 때

각 화면마다 이렇게 적어줘:
1. 사용자가 어쩌다 이 화면을 보게 되는지 (한 줄)
2. 제목과 설명 문구 — 사용자를 탓하지 않는 톤으로
3. 버튼 라벨과 누르면 어디로 가는지
4. 일러스트가 들어갈 자리와 그 자리가 비어도 화면이 깨지지 않는지

문구는 후보를 두 개씩 주고, 어느 쪽을 왜 추천하는지 말해줘.
코드는 건드리지 마. 문서만 쓰는 거야.
```

세션이 짧게 끝났으면 이어서 하나 더 — **디자이너가 개발자에게 넘기는 일**입니다:

```
방금 쓴 스펙을 개발자가 붙이려면 뭐가 필요한지 정리하자.

## 프롬프트

```
피그마에서 한끼 배달앱 파일을 열어줘. 장바구니 화면의 빈 상태(Empty State) 시안을 만들자.
